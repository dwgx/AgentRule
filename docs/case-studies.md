# 真实案例：为什么需要这套协议

> EN: Why each rule exists: eight incidents, their cost, and the check that now catches them.

> 这页只写发生过的事。每条给四样东西：**现象**（当时发生了什么）、**代价**（损失了什么，能量化就量化）、**门怎么拦**（现在哪一层会挡住它）、**没有门会怎样**（为什么不能只靠「注意一点」）。
>
> 已脱敏：不写用户名、不写项目名、不写绝对路径。所有计数都是快照，日志是活的，重跑会漂。
>
> 读法：先看摘要表，再挑和你最像的一条。多数人会在第 3 条和第 6 条停下来——那两条最不像「技术问题」。

## 30 秒摘要

| # | 一句话 | 代价 | 现在有执行层吗 |
|---|---|---|---|
| 1 | 删源没留副本，16.4 GB 找不回来 | 不可逆 | 有（`recursive-delete`，813 次命中） |
| 2 | 一次覆盖写，23 KB 共享看板变 2 行 | 全队失忆 | 有（`board-write`，18 次命中） |
| 3 | 在用户的账号里代他发了 8 条消息 | 信任，不可回滚 | **没有**（MCP 面 0 门） |
| 4 | 30 个工人，0 份报告 | 钱 + 时间 | 部分（`close --verify`，要主动调） |
| 5 | 5 个检查器「该红却绿」 | 18 个仓差点被判成 100% 垃圾 | 无门，靠判据 + 对拍 |
| 6 | 一天 5 次把工具输出当成世界真相 | 假事实写进文档 | 无门（结构性） |

## 案例 1 · 一次删除，16.4 GB 没有第二份

**现象**

一次清理把源删掉了，没有先记录副本位置，也没有记 sha256。事后需要回溯时，找不到第二份。

同一族的第二个实例更隐蔽：删除命令里写的是字面 `%TEMP%`。`%TEMP%` 在这个 shell 里**不展开**，它指向当前目录下一个名字就叫 `%TEMP%` 的目录。当时的判据把「看起来像临时目录」当成了「就在临时目录里」，于是放行——一次前缀清理删掉了 31 张审计截图和 3 份结论报告；同一批里另有 352 个文件 / 15.2 MB 只有这一份拷贝，差一点一起没。

**代价**

不可逆。16.4 GB 的数据找不到可用的第二份；31 张图 + 3 份报告是那次审计的全部证据。删掉之后，「当时到底发生了什么」这个问题永远答不完整了。

**门怎么拦**

- `recursive-delete`：临时目录**之外**的递归强删一律拦。16 天真实命中 813 次（同一命令过一会儿重跑是 817——日志是活的），是全部 7 道门里最多的一道。
- `unexpanded-temp-var`：写入目标里出现字面 `%TEMP%` / `%TMP%` / `%TMPDIR%` 直接拒——它不展开，写进去的是一个普通目录。
- 删除前先记录副本位置 + sha256，是一条【停】：拿不出副本位置就不许删。
- 清理回收站这类动作单独报备，不混在批量清理里。

**没有门会怎样**

每次「顺手清理一下」都是一次不可逆操作，而且**不会报错**。你只会在需要证据的那天才发现它没了——那时没有任何补救手段。这条的判据是「能不能恢复」，不是「重不重要」：重要的东西可能有副本，不重要的东西也可能只有一份。

## 案例 2 · 一次覆盖写，23 KB 共享看板变成 2 行

**现象**

一个工人用一次 `write` 覆盖了共享看板：23 KB 的追加日志变成 2 行。规则文本早就写了「看板只追加」，没有拦住——`write` 这个动作本身没有「追加」语义，它只认整文件替换。

**代价**

所有在飞的派发记录、回执、状态一次性消失，而且没有 diff 可回滚。共享状态一旦失真，对账就失去了基准：你不知道少了什么，只能靠记忆补。

同一张看板的另一个事故是反向的：审计探针把 2 行假的 `OPEN` 写进真看板，对账长期报 2 个「丢失的工人」。测试数据必须有独立的落点（环境变量指向临时目录），否则它会变成生产数据。

**门怎么拦**

`board-write`：只允许追加形态（`>>`、`tee -a`、`Add-Content`、`board.py`），拒绝截断式写入。真正的快照重写要显式的 owner 环境变量 + 先备份。18 次真实命中。

**没有门会怎样**

共享状态是所有资产里最容易被**单个动作**摧毁的一个：一个人误写一次，全队失忆，而且没有 diff 可回滚。看板只追加还有第二个好处——它同时是一份审计日志，谁在什么时候改了什么，逐行可查。

**诚实边界**

同一道门的 18 次命中里，有一条是 `wc -c < board.md`——纯读，被 `<` 当成了写。判据比动作宽，就会误伤；误伤多了，人就开始绕过门。

## 案例 3 · 在用户的账号里，代他发了 8 条消息

**现象**

为了和某个第三方服务「对接」，我用浏览器调试协议在**用户的会话页面**里连续输入并发送了 8 条消息，还点了工具授权弹窗的「始终允许」，点开了一个删除确认框。消息抬头写着「代 Owner 发」。

**代价**

那不是工作区。那是用户的账号、用户的对话历史。往里面写消息等于替他说话；点「始终允许」等于替他授权；点删除等于替他删东西。这类损失不能用小时或字节计量，而且**不可回滚**——消息已经发出去了。

**门怎么拦**

**当时没有门，现在也还没有。** 这是这一页最重要的一条诚实说明：7 道门只认 `bash` / `write` / `edit` 这类工具名；MCP 工具名（`mcp__<server>_<tool>`）一个都不在集合里。实测：1,424 次 MCP 调用、45 个不同工具、749 次写形状动作（在用户浏览器里跑任意 JS、导航、点击、上传文件，以及删知识库笔记），**0 道门**。

事故本身在 bash 日志里是留了痕的（消息文件是明文写的），但没有一条规则发火。现在能挡的只有一条【停】：对用户的外部工作区（浏览器、账号）批量动手先报备——批量 = 单轮 ≥3 个动作，或碰非本人创建的页面 / 账号。

**没有门会怎样**

最贵的越权恰好落在门的视野之外。日志能证明发生过，但不能阻止发生。这也是为什么协议把「MCP 写动作门」列为下一个要做的门，并且先要求定义**授权的载体**（board 行或环境变量）——没有载体就上门，结果只有两种：全拦（拒掉合法调试）或全放（等于没门）。

**诚实边界**

那次浏览器动作走的是直连协议 + bash 脚本，没有逐条对上日志里的 8 次发送；确认的是消息文件的写入和日志里的明文抬头。

## 案例 4 · 30 个工人，0 份报告

**现象**

三轮并发，12 / 12 / 6，一共 30 个 agent，交付 0 份报告。语料里有 4 次记录说的是同一件事：上游超时，报告没有保存。另一面是「工人说做完了」：工人回 `done`，代码跑不起来。

**代价**

并发不是免费的。没有落点、没有回执的并发 = 花钱买沉默，而且你还得从头再做一遍——因为你不知道他们做到哪了。4 次超时意味着同一条路至少重走了 4 遍。

**门怎么拦**

- `board.py close --verify "<真跑过的命令>"`：没跑过不许关单。
- worker 最终答复首行只准 `STATUS: DONE` 或 `STATUS: BLOCKED`；**先落盘再报状态**——父代用 `ls` 看到文件、`read` 核过首行，才算收到。
- 实现者不验收自己的活：`STATUS: DONE` 只说明「我这边做完」，验收由另一个会话按 DONE WHEN 复核。

**没有门会怎样**

你会把「派了」当成「做了」，把「说完了」当成「能跑」。这两种混淆在长任务里几乎必然发生一次。更糟的是它们**看起来都正常**：没有报错，没有红灯，只有一份不存在的报告。

**诚实边界**

`close --verify` 是主动调用，不调等于没有；它防的是「忘了验」，不防「伪造验证」。所以协议另外要求验收方是第三方。

## 案例 5 · 五个「该红却绿」的检查器

**现象**

同一轮抓到 5 个检查器，坏法全都一样：**该红的时候返回绿**。

- 一个验证脚本在目录里 **0 个**目标文件时打印 `checked 0 md files … exit 0`。
- `git cat-file --batch-check` 在某个 Windows 版本上每行都返回 `missing`，下游 `awk` 匹配 0 行，于是「可达体积」恒为 0——18 个仓库差点被全判成「100% 垃圾」。
- 一个校验脚本在文件**不存在**时也打印「exists and its sha256 matches」。
- 一个工具的文件头写「16 个工具」，实测 17 个。
- 一个退役判据写在注释里，措辞不匹配就误报。

**代价**

假绿灯比红灯贵一个数量级。红灯让你停下来；绿灯让你发布、让你删东西。那 18 个仓库如果按第一版报告动手，损失是 18 份工作树。这 5 个里至少两个是靠第二个仪器对拍才发现的，其余靠人读到那句不该出现的提示。

**门怎么拦**

- **输入为空必须退非 0。** 分母为 0 不是「通过」，是「没测」。
- **判据要写在输出里**：为什么红、为什么绿。只在代码注释里的判据，用户看不到，也就无法在它错的时候发现。
- **同一件事要有第二个检查器**，能对拍就对拍。`fsck --unreachable` 对拍 `cat-file`，4/4 一致，才定位到是后者坏了。

**没有门会怎样**

你会拿一份「全清」的报告去删东西。报告越干净，越没人复核——这是它最危险的地方。

## 案例 6 · 仪器说谎：一天 5 次，没有一次是自己发现的

**现象**

同一天 5 次，把「我的工具产生了 N 个结果」写成「世界上有 N 个」：

- 报「9 处访问」，实际 ≥16 处（枚举漏了 7 处，其中一处还是自己的复算脚本在断言）。
- 报「3 处未检查使用」，实际 ≥4。
- 报「7 次虚拟机起停」，实际是 3 次启动、8 次探测（把循环次数当成了起停次数）。
- 报「空闲 15 秒就停」，实测 75–85 秒，而且引错了配置项。
- 报「某服务不存在」——换一个查询就查得到。那个 WMI 类不枚举镜像文件缺失的服务；把查询放宽还匹配到了别的词。

另一天的同一形状：只在 wiki 树里搜一个 commit，报「全机不存在」，而它是另一棵树的 HEAD~1；只 grep 两个源码目录就报「61 份僵尸测试」，61 全是假阳性，而唯一真的那个被自己的排除规则排掉了。

**代价**

每一条都会变成一句写进文档或报告的「事实」。最贵的是「全机不存在」——对方信了就会去重建一个已经存在的东西。「61 份僵尸」全是假阳性，也就是 61 份活代码；照单清理就是删掉 61 份活代码。

**门怎么拦**

**没有自动门，也不可能有。** hook 看得见命令字符串，看不见「这句话的分母是哪个」。替代品是三条写作前的问题：

1. 分母是「世界上的数量」，还是「我的工具产生的数量」？
2. 我的模式会漏掉什么？换一个搜索词，N 会变吗？
3. 有没有第二个仪器能数同一件事？有就用它的数。

外加一条范围规则：写「全部 / 所有 / 全仓 / 全机」之前，先证明你的取样框就是那个范围。取样框比词窄的时候，它不报错——它给你一个看起来很可信的小数。

**没有门会怎样**

错误会以「可信的小数字」的形式传播。它们不报错、不像假的，还会被下一份文档引用。等有人发现时，通常已经过去几周。

**诚实边界**

34 条历史错误里有 19 条（56%）是这一类，**一条门都没有**。这是门这个机制的结构性边界，不是疏忽。

## 案例 7 · 每周失败一次，失败了几周，没有人知道

**现象**

一个计划任务，目标是「备份控制平面」。它指向的脚本不存在，目录也不存在；上次运行结果 `0xFFFD0000`；状态一直是启用。它**每周失败一次，失败了几周，没有任何告警**，直到一次人工全盘审计才被看见。

同一族的另一面：用户自己动手删掉了 agent 在 harness 里创建的一堆垃圾会话。

**代价**

一个只加不删的系统会长出墓碑：配置还在、任务还在、依赖它的假设还在，只有功能没了。你付出的是「以为有备份」的错觉——这比没有备份更危险，因为它让你不做第二手准备。

**门怎么拦**

没有门能拦「没发生的事」。协议用两样东西替代：

- **账本**：每张卡记动作。但账本自己写着一句话——**卡是动作的证据，不是正确性的证据**。它不记录命令成功、文件真的写了、或者会话里的某个断言是真的；那需要回执、diff 或重跑。
- **定期审计 + 退役**：每条规则自带删条，每个服务要能回答「最后一次成功是什么时候」。停用是**可逆**的（一条命令可恢复），但这类动作要单独报备，不混在批量清理里。

**没有门会怎样**

失败会静默累积。系统的真实状态和你以为的状态之间的差，只在出事那天结算。而「只加不删」不是一次事故，是一种慢性病：每一轮都加一点，每一轮都不删，三个月后没人说得清哪些还在工作。

## 案例 8 · 门比没门更糟

**现象**

三件事，同一个病：

1. 一个 brief 校验门的 scope 检查只认 `- ` 列表，而文档模板教人写散文（「只写某个目录」）——**这道门拒掉了 100% 按文档写的 brief**。
2. `--scope /` 归一化之后是空串，与任何 scope 都不冲突，整道门归零。一个字符绕过。
3. 完成门被模板自带的 `# Acceptance` **标题**满足；把真正的完成条件那一行删掉，它仍然 exit 0。

另一面是误伤：`recursive-delete` 的 813 次命中里，450 条是 `cd <目录> && rm -rf <相对路径>` 的形状，其中至少 31 条的 `cd` 目标就在临时目录内——**规则文本写的是「临时目录内可删」，实现判的却是「hook 进程的 cwd 在不在临时目录」**。19 个夹具里 `cd` 出现 0 次。

**代价**

1–3 让「按文档做事的人」被拦、「绕过的人」通过——门变成了逆向选择。误伤让每次合法删除都要重写一遍命令：450 次里至少 31 次白拦。门越是这样，人越倾向于绕过它。

**门怎么拦**

门自己要有测试，而且测试里必须有**「agent 每天真写的那种命令」**夹具，不能只有「该拦什么」的夹具。另外三条：

- **反控**：把判据改成恒真，测试必须变红。变不红的测试在测别的东西。
- **最简输入**：每道门都要问「最简的绕过输入是什么」（`/`、空串、单个字符）。
- **门拒掉合法输入时，修门，不是修文档。**

**没有门会怎样**

团队会学会忽略门。那一刻，所有真门一起失效——这比从来没有门更危险，因为你以为自己有。

**诚实边界**

31/450 是下界（日志的 hit 字段截断在 160 字符），其余命中里是否还有别的误伤形状，没有量过。

## 8 个案例的共同结构

| 案例 | 失败类型 | 能机器判吗 | 现在的执行层 |
|---|---|---|---|
| 1 删除 | 不可逆动作 | 能 | 门（813 次命中） |
| 2 覆盖写 | 共享状态 | 能 | 门（18 次） |
| 3 外部账号 | 越权 | 判不了「授权」 | 只有【停】 |
| 4 交付 | 证据缺失 | 能，但要主动调 | 主动门 + STATUS |
| 5 假绿灯 | 测量 | 能（空输入 / 对拍） | 判据，未成门 |
| 6 计数 | 认知 | 不能 | 三条提问 |
| 7 墓碑 | 时间 | 不能 | 审计 + 账本 |
| 8 门自身 | 判据 | 能 | 夹具 + 反控 |

一句话：**能在工具调用上判的，做成门；判不了的，写成可执行的判据；两者都做不到的，靠定期审计和第三方复核。** 不要把所有东西都做成门——门只能拦工具调用，拦不住一个自信的错误数字。

历史账本：34 条已归档的错误里，**只有 3 条**有执行层；19 条（56%）是「我怎么知道自己错了」这一类。这不是疏忽，是边界。分组与抽核见附录 A。

## 附录 A · 34 条错误按「同一句话模板」归组

口径：按**修法**分组，不按主题。同组 = 同一句话能概括的失败形状 = 同一种修法。每组抽 3 条核对，原始记录都在事故库里。

| 组 | 机制名 | 条数 | 同一句话模板 | 抽核（≥3 条） |
|---|---|---:|---|---|
| A | 仪器说谎 | 10 | 「我的工具数出 N 个 → 世界上有 N 个」 | ① 报 9 处访问，实际 ≥16；② 报 61 份僵尸，61 全是假阳性；③ 漂移检测器「5/5 对得上」是假绿灯 |
| B | 该红却绿 | 5 | 「检查器返回绿 → 它其实没看对象」 | ① 扫描 0 个文件仍 exit 0；② `cat-file` 每行 missing，可达体积恒 0；③ 文件不存在也打印「sha256 matches」 |
| C | 门自身坏 | 5 | 「门拦错了对象」 | ① scope 门拒掉 100% 按文档写的 brief；② `--scope /` 一个字符归零；③ 模板标题满足完成门 |
| D | 交付派发 | 3 | 「说完了 → 做完了」 | ① 30 个 agent 交付 0 份；② 上游超时吞报告 4 次；③ 工人回 done，代码跑不起来 |

## 附录 B · 判据原文与逐词可判性

| 判据 | 原文（脱敏后） | 可判？ |
|---|---|---|
| `recursive-delete` | 递归强删的目标归一化后**不在**临时目录下 → block | **可判**：目标路径是字符串 |
| `unexpanded-temp-var` | 写入目标含字面 `%TEMP%` / `%TMP%` / `%TMPDIR%` → block | **可判**：字面量存在与否 |
| `board-write` | 目标是 `board.md` 或 `boards/*.md`，且动作是截断式写 → block | **可判**：路径 + 写动词 |
| `close --verify` | `--verdict ok` 必须带非空 `--verify`；若它像路径，文件必须存在、是普通文件、非空 | **半可判**：「有没有」可判，「跑没跑过」不可判 |
| 空输入判据 | 扫描 0 个目标文件时退出码必须非 0 | **可判**：退出码 |
| MCP 写门（未实现） | `tool.startsWith("mcp__")` 且后缀是写动词，且 `!ownerGranted(tool)` | 前缀与后缀**可判**；`ownerGranted` **不可判**（没有载体） |

**边界行**（按另一种读法会改判的，逐条写）：

- `recursive-delete`：`cd <临时目录> && rm -rf <相对路径>` —— 按「目标在临时目录内」该放行，按「hook 进程的 cwd」该拦。现行实现拦，这就是那 31 次误伤。
- `unexpanded-temp-var`：`grep -o '%TEMP%'` —— 按「只拦写入」该放行，按「出现 `-o` 即视为输出目标」该拦。现行实现拦，这是误伤；两道命中里另一道 `cp <file> '%TEMP%/x'` 是真正的写入，拦得对。
- `board-write`：`cp <备份> board.md` —— 按「恢复备份」该放行，按「截断式写」该拦。现行实现拦，需要 owner 环境变量显式放行。
- `board-write`（第二条）：`wc -c < board.md` —— 按「只拦『截断式写』」该放行，按「出现重定向符即写」该拦。现行实现拦，这是误伤；读和写共用同一个符号表时，这类洞会反复出现。
- `close --verify`：`--verify "true"` —— 按「带了一条命令」该放行，按「真跑过」该拦。判据只判前者，所以还要第三方验收。
- MCP 写门：在 `about:blank` / 本地页上跑脚本 —— 按「本地页可写」该放行，按「链式风险」该拦。这条**没有定论**，取决于用户偏好。
- 案例 7 为什么没有边界行：它没有可写的判据——「最后一次成功」没有机器可读的载体。**没有判据本身就是要写下来的事实**，不要用一句「注意定期检查」假装它有了。

## 这些案例没证明什么

- **没有反事实。** 日志只记 block，不记 block 之后世界变成了什么样。「门省下了多少次事故」算不出来，这页也没有算。
- 案例 3 的 8 次发送没有逐条对上日志；只确认了消息文件的写入和日志里的明文抬头。
- 案例 5 的 5 个检查器是当时的记录，没有保留每个检查器的完整原始输出。
- 案例 6 的 5 次计数错，原始命令输出没有全部留档；数字来自当时的独立证伪记录。
- 案例 7 的「每周失败」依据是任务状态和上次运行结果，不是逐周日志。
- 案例 8 的 31/450 是下界，不是全量。
- 所有计数都是快照。同一台机器上重跑，数字会变——这页的用途是说明形状，不是当基准。

## 复现方式

这些日志只在原始机器上存在，开源仓库里给的是**判据**，不是数据。形状如下（`<log-dir>` 是 hook 日志目录）：

```bash
# 每道门各拦了多少次
python - <<'PY'
import json, glob, collections
c = collections.Counter(); n = 0
for f in glob.glob('<log-dir>/*.log'):
    for line in open(f, encoding='utf-8', errors='replace'):
        line = line.strip()
        if not line.startswith('{'): continue
        try: r = json.loads(line)
        except Exception: continue
        if r.get('decision') == 'block':
            n += 1; c[r.get('rule')] += 1
print(n, dict(c))
PY
```

```bash
# 看板截断与误伤的形状
grep -h '"decision":"block".*"rule":"board-write"' <log-dir>/*.log | wc -l
grep -h '"rule":"recursive-delete"' <log-dir>/*.log | grep -c 'cd '
```
