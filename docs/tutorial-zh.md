# 使用教程：把这个仓库交给你的 AI 助手

> EN: User tutorial — hand this repository to your AI agent; it deploys, asks, verifies, and can roll back.
>
> 这份文档在仓库里的位置：`docs/tutorial-zh.md`。

**写给谁**：会用终端、但没接触过 AI 助手配置的人。你不需要懂编程，也不需要先背一遍规则。你只要做三件事：下载、把文件夹交给 agent、回答它的问题。

---

## 1. 这是什么

这是一套**写给 AI（人工智能）助手看的做事规矩**，外加一份**让它自己安装的说明书**。

你把整个文件夹交给你的 AI 助手，它会先检查你的电脑、问你几个问题，然后把规矩装进你正在用的那个 AI 工具里。装好之后，这个助手每次开新对话都会先看到这些规矩：哪些事绝对不能做、活要怎么交、出错怎么恢复。它不改你的代码，也不换你的模型。

先把几个词说清楚：

- **agent（AI 助手）**：能在你电脑上读文件、跑命令、改代码的人工智能。Claude Code、Codex、omp 都是这类工具（都在终端里跑），也是 agent 的入口。
- **harness（外壳）**：启动 agent 的那层程序。可以理解成驾驶座：agent 是司机，harness 是车。它决定 agent 从哪里读配置、能调用哪些工具、能不能在危险动作前拦截。Claude Code、Codex、omp 是三辆不同的车，同一套规矩装进去的位置不一样。
- **仓库（repo）**：一个文件夹，除了文件本身，还记录每次改动。GitHub 上的项目就是一个仓库。

仓库里的部署协议有一个编号 `ADP-1`。协议就是一套规定好顺序的动作清单。agent 开始执行时，会在第一条回复里带上这个编号，你可以用它确认对方读的是这一版。

## 2. 为什么需要它

讲一个很常见的场景。

你让 agent 清理临时文件。它为了省事，跑了一条「递归强删」命令（一条命令把目录和里面所有东西一起删掉），把项目里的 `.git` 目录一起删了——那是项目的版本历史，没了就没了。你当场纠正它：「以后删东西之前先确认。」它回答：「好的，记住了。」

第二天你新开一个对话，让它再清理一次。它又跑了同一条命令。

不是它故意气你，是它真的不记得了。默认情况下，agent 的记忆只存在于**当前这次对话的上下文**里。上下文就是它这次能看到的全部文字，有长度上限，按 **token** 计。token 是模型处理文字的最小单位，大约一个英文单词或半个汉字；上下文越长，越贵，也越容易把重点稀释掉。你一关对话，或者上下文被压缩，昨天那句「以后别这样」就没了。

这套仓库解决的就是这件事：把「出过事故才换来的规矩」写成文件，装到 agent 每次启动都会读的位置。新对话一开始，它先看到这些规矩，而不是从零开始。

其中一部分规矩可以配成 **hook**。hook 是挂在 agent 动作前的一小段检查程序：agent 要跑命令、写文件时，先过它一遍；命中写死的危险规则就直接拒绝。它不联网，只按几条固定规则判断。

还有一类叫 **skill**：一份按需打开的操作说明。agent 平时不读它，遇到对应任务才读，比如「收工交接」有一份 skill，「查这台机器装了什么」有一份 skill。这样既不占每次启动都带着的上下文，又能在需要时拿到详细步骤。

## 3. 怎么用：三步

### 第一步：下载

打开这个仓库的 GitHub 页面，点绿色的 `Code` 按钮 → `Download ZIP`（下载压缩包），解压到一个你找得到的位置（比如桌面）。解压出来的文件夹就是「仓库」。

如果你电脑上有 git，也可以：

```bash
git clone <这个仓库的地址>
```

git 是记录文件改动的工具；clone 就是把远程仓库完整复制一份到本地。两种方式选一种即可，不需要再装 Python、Node 之类的编程语言运行环境——安装脚本只用系统自带的 PowerShell（Windows 自带的命令行工具）或 bash（macOS / Linux 自带的命令行工具）。

### 第二步：把文件夹交给 agent

打开你平时用的 agent，让它能看到这个文件夹。最稳的做法：在终端里先 `cd`（切换目录）进仓库目录，再启动 agent。

然后原样粘贴下面这段话。这段话叫 **prompt（提示词）**，就是你给 agent 的指令：

```text
读这个仓库里的 install/BOOTSTRAP.md（引导文件），按它说的帮我部署。
先探测，再问我；不确定就停下来问，不要猜。
动手前先把「要改哪些文件 + 备份到哪」列给我看。
```

它应该先读文件、检查你的环境，然后开始提问。**如果它一上来就改文件、一个问题都没问，打断它**，说：「先停。按 BOOTSTRAP 的流程走，先给我计划。」

### 第三步：回答它的问题

它会把要问的一次列出来（每轮最多 4 个），每个问题带编号、选项、默认值和「猜错的后果」。你按编号回答就行。

答完它会给你一份计划：要改哪些文件、备份到哪、怎么验收、怎么回滚。**看完再点头。** 计划里如果有你不认识的路径，直接问它「这个文件是干什么的」。

它装完必须交三样东西，缺一样就是没交：

1. 改了什么（文件路径 + 备份路径）；
2. 验收命令的原样输出（不是它自己说「通过了」）；
3. 怎么退（一条能直接跑的回滚命令）。

三套 harness 的具体装法不在这篇里，在 `adapters/`（适配文档目录）：omp 看 `adapters/omp.md`，Codex 看 `adapters/codex.md`，Claude Code 看 `adapters/claude-code.md`。不知道自己用的是哪个，看 `adapters/README.md` 的选择表，或者把启动命令告诉 agent 让它判断。

## 4. 它会问你什么（3 个例子 + 标准答案）

它只问「磁盘上查不到」的东西：你的偏好、授权、意图。版本、路径、装没装过这类问题，它应该自己查，不该问你。

### 例子 1：用哪个 harness

> **它问**：「我探测到你电脑上有 omp 和 Claude Code。你平时用哪个？可以多选。」

**它在确认**：装到哪套配置里。装错位置等于没装。

**标准答案**：
> 「我只用 omp，装 omp 就行。不确定的话按你探测到的那个装，不要一次装三套。」

（把 `omp` 换成你实际在用的那个。）

如果你确实三套都用，可以说「三套都装」，但要接受它要改三个地方、出问题也更难排查。第一次装，建议只装一套。

### 例子 2：已经有规则文件了，怎么处理

> **它问**：「这几个入口文件里已经有你的规则。追加、单独放一份加一行指针、还是先备份再替换？」

**它在确认**：会不会覆盖你攒了很久的东西。这是会动到原有内容的问题，拿不准就明确说「追加」，不要只说「你定」。

**标准答案**：
> 「追加。先备份，只加你那段带标记的内容，不要动我原来的。改完把差异（diff）贴给我看。」

diff 就是两份文件的差异清单，能看出它到底改了哪几行。

### 例子 3：装全局还是装项目里

> **它问**：「装到当前用户的家目录（推荐），还是别的地方（比如当前这个项目）？」

**它在确认**：规则的生效范围。

**标准答案**：
> 「装全局，也就是我的用户目录。我要所有项目都用同一套规矩，不要装进项目仓库。」

装进项目仓库的坏处：换个目录就失效，而且会把规则文件混进你的代码提交里。

### 还可能问到的

- **「要不要开 hook（自动拦截）？」** → 标准答案：「开。它只在几种危险动作上拦（递归强删、杀错进程之类），平时不打扰。」但别把它当万能保险：它只覆盖这套 harness 真正挂上的那几种动作。
- **「允许我执行仓库里的安装脚本吗？」** → 标准答案：「先跑 dry-run（只打印计划、不写文件），把计划给我看；我点头再真装。」陌生脚本默认不该直接跑。
- **「可以动 git 或联网吗？」** → 标准答案：「都不用。这个仓库不需要联网，也不要帮我 commit / push（提交 / 推送代码），更不要改这个仓库本身。」
- **「hook 拦住了写入，怎么办？」** → 标准答案：「换一个不被拦的路径，或者告诉我需要手动放行哪一步；不要自己关掉 hook。」
- **「你说的和你机器上探测到的不一样。」** → 以探测为准，让它把差异贴出来，再决定。

## 5. 装完怎么确认（一条命令）

在**仓库根目录**（能看到 `install` 文件夹的那一层）打开终端，跑对应系统的那条：

**Windows（PowerShell）**

```powershell
powershell -NoProfile -File install/verify.ps1
```

**macOS / Linux**

```bash
bash install/verify.sh
```

它会一行一行检查，每行以 `PASS`（通过）、`FAIL`（失败）或 `SKIP`（跳过：缺工具或缺基线）开头。最后会打印一行 `[summary]` 和一行 `VERDICT:`：

- `VERDICT: PASS (exit 0)` —— 全部检查通过；
- `VERDICT: FAIL (exit 1)` —— 至少一项没通过；
- `VERDICT: PARTIAL (exit 2)` —— 没有失败，但有跳过项（比如本机没装某个检查工具）。

`VERDICT` 后面的 `exit 0/1/2` 就是退出码：0 = 成功，1 = 有失败，2 = 有跳过。只有 `VERDICT: PASS` 才算完全装对；出现 `PARTIAL` 时，把 `SKIP` 那几行原文发给 agent，让它判断是环境缺工具还是真有问题。

**这条命令能证明什么**：该在的文件都在、内容和仓库里的一致、入口文件里的标记块（带 `BEGIN` / `END` 注释的那一段）在。

**它不能证明什么**：不能证明你的 harness 真的把规则读进了模型上下文，也不能证明 agent 以后不犯错。它只检查「装」这一层。

想再确认一步：**重开一个 agent 会话**（入口文件只在启动时读一次），问它：「你现在读到的规则入口是哪个文件？」它能说出入口文件的路径，说明新会话确实读到了。这一步是行为检查，不是硬验收；答不上来就把现象告诉 agent，让它查对应的适配文档。

**如果出现 `FAIL` 或 `VERDICT: FAIL`**：把那一行原文、以及它上面几行，一起复制给 agent。不要自己改脚本让它变绿——检查红了要改的是安装，不是检查。

## 6. 出问题了怎么办

### 先分清三种「不对」

| 现象 | 大概率原因 | 先做什么 |
|---|---|---|
| 验收命令里有 `FAIL` 或 `VERDICT: FAIL` | 文件没装全 / 内容不一致 | 把 FAIL 行原文贴给 agent，让它按 `install/INSTALL.md` 修 |
| 验收命令是 `VERDICT: PASS`，但 agent 行为没变化 | 没重开会话，或 harness 没加载入口文件 | 重开一个会话再试；还不行就让 agent 查 `adapters/` 对应那篇 |
| 装到一半报错 | 权限、路径、编码、文件被占用 | 让 agent 走回滚，确认回到安装前，再决定要不要重装 |

### 回滚（撤销这次安装）

安装器在覆盖任何已有文件之前都会备份，备份目录是安装根目录下的 `.backup-<时间戳>/`（例如 `C:\Users\你的名字\.backup-20261102-101500\`）。agent 交活时必须给你一条能直接跑的回滚命令；如果它没演练过，它应该写「未演练」，而不是「应该可以」。

手动回滚三步：

1. 打开备份目录，把里面的文件**按相对路径**拷回原位，覆盖新文件；
2. 删掉这次**新建**的文件（清单在它给你的计划/报告里）；
3. 如果只是想暂时停用、不想全删：打开入口文件，删掉从 `<!-- BEGIN agentrule:entry v1 -->`（托管块开始）到 `<!-- END agentrule:entry v1 -->`（托管块结束）这一段。

入口文件的位置每套 harness 不同：omp 是 `~/.omp/agent/AGENTS.md`，Codex 是 `~/.codex/AGENTS.md`，Claude Code 是 `~/.claude/CLAUDE.md`；以 `adapters/*.md` 里写的为准。

**不要**直接删整个 `.claude` / `.codex` / `.omp` 目录——那里面还有你自己的配置和历史。只动这次清单里的文件。

### 如果 hook 拦了你的正常操作

把拒绝信息原文贴给 agent，让它判断是「真危险」还是「误拦」。不要为了通过就把整个 hook 关掉——那等于把门拆了。误拦应该改规则或改命令，不是关检查。

### 最坏情况

这套东西只写它自己的规则目录、入口文件和配套的 skill 目录，默认不碰你的项目代码。最坏情况是「装了一半」：按上面的回滚步骤把备份拷回去、删掉新增文件，就回到装之前。你的代码不会因为它被改坏——除非你另外让它改代码，那是另一件事。

## 7. 常见误解

**① 「这是给我读的说明书。」**
一半对。安装时你要开场、回答、看计划；装完之后你不用背规矩。规矩的读者是 agent。

**② 「装上就不会再犯错了。」**
不会。它减少的是「同一个错反复犯」，不是消灭错误。hook 只覆盖少数写死的动作（比如递归强删、杀错进程），模型仍然可能不遵守文字规矩。

**③ 「它会改我的代码，或者让模型变聪明。」**
都不会。它不改模型、不改你的项目代码，只改 agent 启动时读到的规矩和可用的检查。

**④ 「三套 harness 装法一样，随便看一篇就行。」**
不一样。omp、Codex、Claude Code 的入口文件和加载机制不同，必须看对应的 `adapters/*.md`。装错位置，文件在、但不生效。

**⑤ 「规则写得越多越安全。」**
反了。每次启动都带着的上下文越长，越贵、越稀释重点。这套规矩自己规定：只有四种情况才加规则（同一个错犯第二遍、审计抓到、同一句纠正重复出现、新同事需要上下文），而且每条新规则要写「什么条件下可以删」。

**⑥ 「token 是账号、密码或者充值币。」**
不是。这里 token 是模型处理文字的最小单位，用来算上下文长度和费用。它和登录凭据不是一回事。

**⑦ 「这是安全软件 / 防火墙。」**
不是。它不杀毒、不防黑客，也不防你自己手滑。它是一套行为规矩，加少量本地拦截；真正的安全边界要靠备份、权限和谨慎操作。

**⑧ 「装完就一劳永逸。」**
不会。你以后纠正 agent 的新问题，可能要往规则里加一条；换 harness、换机器要重装；规则本身也有删除条件，会随事故和纠正更新。

## 8. 术语小抄

| 词 | 一句话解释 |
|---|---|
| agent | 能在你电脑上读文件、跑命令、改代码的 AI 助手 |
| harness | 启动 agent 的外壳，决定它读哪些配置、能用哪些工具、能不能拦截危险动作 |
| hook | 挂在 agent 动作前的小检查程序，命中写死的规则就拒绝执行 |
| skill | 一份按需打开的操作说明，agent 遇到对应任务才读，不占每次启动都带着的上下文 |
| token | 模型处理文字的最小单位，约一个英文单词或半个汉字；上下文长度和费用按它算 |
| 上下文 | agent 当前这次对话里能看到的全部文字，有长度上限 |
| prompt | 你发给 agent 的那段指令文字 |
| 仓库（repo） | 一个记录改动历史的文件夹；GitHub 上的项目就是一个仓库 |
| Markdown | 一种纯文本排版格式，文件名以 `.md` 结尾，用 `#` 表示标题 |
| 终端 | 敲命令的窗口（Windows 的 PowerShell、macOS/Linux 的 Terminal 都算） |
| dry-run | 「只说不做」：打印准备改什么，但一个字节都不写 |
| diff | 两份文件的差异清单，能看出改了哪几行 |
| 回滚（rollback） | 撤销这次安装，把文件恢复到装之前的样子 |
| 入口文件 | agent 每次启动都会读的那个文件；规矩就是从这里被带进上下文的 |
| 适配文档 | 每套 harness 一份的安装说明，在 `adapters/` 目录下 |

这篇教程只讲「你会看到什么、你要做什么」。具体到每个文件写在哪、配置怎么合并，看上面的适配文档和安装文档——那是 agent 执行时读的，不是让你背的。

---

**一句话总结**：下载仓库 → 把文件夹交给 agent，让它读 `install/BOOTSTRAP.md` → 它问什么你答什么 → 跑 `install/verify.ps1`（或 `verify.sh`）确认 → 不对就按备份回滚。
